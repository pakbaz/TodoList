# TodoList Infrastructure as Code and CI/CD Implementation Plan

## Executive Summary

This implementation plan outlines the deployment strategy for the TodoList ASP.NET Core Blazor application to Azure Container Apps using Infrastructure as Code (Bicep) and CI/CD (GitHub Actions). The solution follows Microsoft's Well-Architected Framework principles, emphasizing security, reliability, and operational excellence.

## Architecture Overview

Based on the architecture analysis, this is a **monolithic .NET 9 Blazor Server application** that will be deployed as a **single container** to Azure Container Apps with Azure PostgreSQL Flexible Server as the database backend.

## Azure Resource Strategy

### Target Azure Resources

1. **Resource Group** - Container for all resources with consistent naming
2. **Azure Container Registry (ACR)** - Store application container images
3. **Azure PostgreSQL Flexible Server** - Managed database service with high availability
4. **Azure Key Vault** - Secure secrets and connection string management
5. **Log Analytics Workspace** - Centralized logging and monitoring
6. **Application Insights** - Application performance monitoring
7. **Azure Container Apps Environment** - Hosting environment with observability
8. **Azure Container App** - Application instance with auto-scaling

### Resource Dependencies and Order

1. **Foundation Layer** (Parallel deployment):
   - Resource Group
   - Log Analytics Workspace
   - Azure Key Vault

2. **Database Layer**:
   - Azure PostgreSQL Flexible Server
   - Database user creation for managed identity

3. **Container Infrastructure**:
   - Azure Container Registry
   - Container Apps Environment

4. **Application Layer**:
   - Container App deployment

## Security Strategy

### Zero-Secret Architecture

- **OIDC Authentication**: GitHub Actions to Azure using federated identity credentials
- **Managed Identity**: System-assigned managed identity for Container App
- **Key Vault Integration**: Database connection strings stored securely
- **Passwordless Database**: Microsoft Entra ID authentication to PostgreSQL

### Security Best Practices

- **Principle of Least Privilege**: Minimal required permissions for each identity
- **Network Security**: Private endpoints and network isolation where applicable
- **HTTPS Enforcement**: All communication encrypted in transit
- **Secret Management**: No secrets in code or configuration files
- **Container Security**: Non-root user execution, minimal base image

## Infrastructure as Code (Bicep) Strategy

### Modular Template Design

```
/infra/
├── main.bicep                    # Main orchestration template
├── parameters/
│   ├── dev.bicepparam           # Development environment parameters
│   ├── staging.bicepparam       # Staging environment parameters
│   └── prod.bicepparam          # Production environment parameters
└── modules/
    ├── resource-group.bicep     # Resource group module
    ├── container-registry.bicep # ACR module
    ├── postgresql.bicep         # Database module
    ├── key-vault.bicep          # Key Vault module
    ├── log-analytics.bicep      # Monitoring module
    ├── container-apps.bicep     # Container Apps environment
    └── container-app.bicep      # Application instance
```

### Bicep Best Practices Implementation

- **Parameterized Templates**: Environment-specific configurations
- **Secure Outputs**: Sensitive data marked with @secure() decorator
- **Naming Conventions**: Azure Cloud Adoption Framework naming standards
- **Resource Tagging**: Consistent tagging for cost management and governance
- **Idempotent Deployments**: Safe re-deployment without resource destruction
- **Validation Rules**: Parameter validation with @allowed decorators

### Configuration Strategy

- **Environment Separation**: Distinct parameter files for dev/staging/prod
- **Resource Naming**: Deterministic naming with environment prefixes
- **SKU Selection**: Cost-optimized SKUs for non-production environments
- **Scaling Configuration**: Environment-appropriate scaling parameters

## CI/CD Pipeline Strategy

### GitHub Actions Workflow Design

```
/.github/workflows/
└── deploy.yml                   # Main deployment workflow
```

### Pipeline Architecture

1. **Infrastructure Deployment Job**:
   - Bicep template validation
   - Infrastructure provisioning
   - Resource configuration

2. **Application Deployment Job**:
   - Container image build
   - Image push to ACR
   - Container App deployment
   - Health verification

### Deployment Strategy

- **Branch-based Environments**: 
  - `main` branch → Production
  - `develop` branch → Staging
  - Feature branches → Development
- **Infrastructure-first**: Ensure infrastructure exists before application deployment
- **Atomic Deployments**: Rollback capability for failed deployments
- **Health Checks**: Automated verification of deployment success

### Security Integration

- **OIDC Authentication**: No stored secrets in GitHub repository
- **Environment-specific Service Principals**: Separate identities per environment
- **Least Privilege Access**: Minimal required permissions for deployments
- **Secret Scanning**: Automated detection of accidentally committed secrets
